本文完整整理 A5.1—A5.6 的实现方案、代码、执行顺序和验证方法，供你按顺序手动编写。

所有内容都按照当前项目的技术栈编写：

- 同步 SQLAlchemy。
- FastAPI 依赖注入。
- Pydantic 嵌套配置。
- Alembic 迁移。
- `ApiError` 和 `ok()` 响应格式。
- pytest 数据库集成测试。

**本文中的代码、迁移和命令需要你手动执行。保存这份教程不会自动修改应用代码或执行迁移、测试。**

有两个范围说明：

1. 为了让跨组织 HTTP 测试有真实对象，需要提前实现 A6 中的“项目详情”和“修改项目描述”。这里不实现完整项目模块。
2. 当前没有运行表和 outbox 表，因此先建立调度角色、独立连接和授权方案。outbox、幂等表的策略提供在后面，随对应表的迁移一起执行。

## 一、先建立整体认识

最终的请求流程是：

```text
浏览器携带会话 Cookie
        │
        ▼
auth_service 连接
检查会话、账号、组织
        │
        ▼
构造 Principal
只携带 org_id、user_id、role
        │
        ▼
业务服务开启 app_runtime 事务
设置事务级组织、用户上下文
        │
        ▼
应用权限检查 + 带组织条件的查询
        │
        ▼
PostgreSQL RLS 再次限制可见行
        │
        ▼
提交或回滚
事务上下文失效，连接归还连接池
```

这里有三道不同的控制：

| 控制 | 负责什么 |
|---|---|
| 数据库对象权限 | 业务连接不能读取认证表，调度连接不能读取业务正文 |
| RLS | 业务连接只能访问当前组织的数据 |
| 应用权限 | writer 不能管理成员，reviewer 不能编辑项目 |

**RLS 不会自动判断 writer 能不能管理成员。应用权限也不能代替 RLS。**

下面开始逐步编写。

## 二、A5.1：创建数据库角色，交接现有表所有权

### A5.1.1 创建角色初始化脚本

新建：

`E:\code\project\harness\scripts\sql\bootstrap_roles.sql`

完整内容：

```sql
DO $$
DECLARE
    target_role text;
BEGIN
    FOREACH target_role IN ARRAY ARRAY[
        'migration_owner',
        'app_runtime',
        'auth_service',
        'ops_runtime'
    ]
    LOOP
        IF NOT EXISTS (
            SELECT 1
            FROM pg_roles
            WHERE rolname = target_role
        ) THEN
            EXECUTE format(
                'CREATE ROLE %I LOGIN',
                target_role
            );
        END IF;

        EXECUTE format(
            'ALTER ROLE %I WITH
                LOGIN
                NOSUPERUSER
                NOCREATEDB
                NOCREATEROLE
                NOREPLICATION
                NOBYPASSRLS
                NOINHERIT',
            target_role
        );

        EXECUTE format(
            'ALTER ROLE %I SET timezone TO %L',
            target_role,
            'UTC'
        );
    END LOOP;
END
$$;

DO $$
BEGIN
    EXECUTE format(
        'GRANT CONNECT ON DATABASE %I TO
            migration_owner,
            app_runtime,
            auth_service,
            ops_runtime',
        current_database()
    );

    EXECUTE format(
        'GRANT CREATE ON DATABASE %I TO migration_owner',
        current_database()
    );
END
$$;

REVOKE CREATE
ON SCHEMA public
FROM PUBLIC, app_runtime, auth_service, ops_runtime;

GRANT USAGE, CREATE
ON SCHEMA public
TO migration_owner;
```

这与前一小节教程的作用相同，但把事务交给调用方控制，方便后面的测试复用。

几个关键点：

- 角色不存在才创建，因此可以重复运行。
- 每次运行都会重新确认低权限属性。
- `migration_owner` 可以在当前数据库创建 schema。
- `migration_owner` 没有创建数据库、创建角色或绕过 RLS 的属性。
- 不给任何运行时角色授予 `migration_owner` 成员身份。

### A5.2.3 提取数据库配置类型

新建：

`E:\code\project\harness\backend\app\core\database_config.py`

```python
from pathlib import Path
from typing import Literal, Self

from pydantic import BaseModel, ConfigDict, Field, SecretStr, model_validator
from pydantic_settings import BaseSettings, SettingsConfigDict
from sqlalchemy.engine import URL

BASE_DIR = Path(__file__).resolve().parents[3]


class DbSettings(BaseModel):
    """同步 PostgreSQL 连接配置。"""

    model_config = ConfigDict(extra="forbid")

    host: str = Field(min_length=1)
    port: int = Field(default=5432, ge=1, le=65535)
    username: str = Field(min_length=1)
    hashed_password: SecretStr = Field(min_length=1)
    name: str = Field(min_length=1)

    driver: Literal[
        "postgresql+psycopg2",
        "postgresql+psycopg",
    ] = "postgresql+psycopg2"

    @property
    def url(self) -> URL:
        return URL.create(
            drivername=self.driver,
            username=self.username,
            password=self.hashed_password.get_secret_value(),
            host=self.host,
            port=self.port,
            database=self.name,
        )


class MigrationSettings(BaseSettings):
    """只在迁移命令中实例化。"""

    model_config = SettingsConfigDict(
        env_file=BASE_DIR / ".env.migration",
        env_file_encoding="utf-8",
        env_nested_delimiter="__",
        extra="forbid",
        case_sensitive=False,
    )

    migration_db: DbSettings

    @model_validator(mode="after")
    def validate_role(self) -> Self:
        if self.migration_db.username != "migration_owner":
            raise ValueError("迁移连接必须使用 migration_owner")
        return self


class AdminSettings(BaseSettings):
    """只供初始化和测试数据库管理使用。"""

    model_config = SettingsConfigDict(
        env_file=BASE_DIR / ".env.admin",
        env_file_encoding="utf-8",
        env_nested_delimiter="__",
        extra="forbid",
        case_sensitive=False,
    )

    admin_db: DbSettings
```

为什么单独放这个文件？

因为 Alembic 只需要迁移配置。它导入配置类型时，不应该顺便实例化整个应用配置、要求提供认证和业务密码。

另外：

```python
URL.create(...)
```

比手动拼接连接字符串可靠。密码包含 `@`、`/`、`%` 时不需要自己做 URL 转义。[SQLAlchemy 官方说明](https://docs.sqlalchemy.org/en/20/core/engines.html#creating-urls-programmatically)

这里故意不使用 `@computed_field`，避免数据库 URL 被当作配置序列化字段输出。

EnvName = Literal["dev", "test", "prod"]


class Settings(BaseSettings):
    """应用配置根模型。"""

    model_config = SettingsConfigDict(
        env_file=BASE_DIR / ".env",
        env_file_encoding="utf-8",
        env_nested_delimiter="__",
        extra="forbid",
        case_sensitive=False,
    )

    env: EnvName = "prod"

    db: DbSettings
    auth_db: DbSettings
    ops_db: DbSettings

    redis: RedisSettings
    security: SecuritySettings

    @model_validator(mode="after")
    def validate_database_connections(self) -> Self:
        expected_roles = (
            (self.db, "app_runtime"),
            (self.auth_db, "auth_service"),
            (self.ops_db, "ops_runtime"),
        )

        for config, expected_role in expected_roles:
            if config.username != expected_role:
                raise ValueError(f"数据库连接必须使用 {expected_role}")

        target = (self.db.host, self.db.port, self.db.name)

        for config in (self.auth_db, self.ops_db):
            if (config.host, config.port, config.name) != target:
                raise ValueError("业务、认证和调度连接必须指向同一数据库")

        return self


settings = Settings()

### A5.2.8 修改 Alembic 连接

替换 [env.py](../migrations/env.py)：

```python
from logging.config import fileConfig

from alembic import context
from sqlalchemy import create_engine, pool

from backend.app import models  # noqa: F401
from backend.app.core.database_config import MigrationSettings
from backend.app.db.base import Base

config = context.config

if config.config_file_name is not None:
    fileConfig(config.config_file_name)

database_url = MigrationSettings().migration_db.url
target_metadata = Base.metadata


def run_migrations_offline() -> None:
    context.configure(
        url=database_url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
        include_schemas=True,
        compare_type=True,
    )

    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = create_engine(
        database_url,
        poolclass=pool.NullPool,
    )

    try:
        with connectable.connect() as connection:
            context.configure(
                connection=connection,
                target_metadata=target_metadata,
                include_schemas=True,
                compare_type=True,
            )

            with context.begin_transaction():
                context.run_migrations()
    finally:
        connectable.dispose()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

这里有两个修正：

- 迁移明确使用 `migration_owner`。
- 显式导入全部模型，让 `Base.metadata` 知道有哪些表。

不再把密码 URL 写进 Alembic 配置字符串，因此也不需要原来的 `%` 转义代码。

### A5.2.9 新增认证权限迁移

执行：

```powershell
uv run alembic revision -m "0002_identity_permissions"
```

生成文件后，保留 Alembic 生成的 `revision` 和 `down_revision`。

目前上一版迁移 ID 应该是：

```python
down_revision = "7e4a6d55dbbc"
```

把迁移主体写成：

```python
from alembic import op


def upgrade() -> None:
    op.execute(
        """
        REVOKE ALL PRIVILEGES
        ON SCHEMA auth
        FROM PUBLIC, app_runtime, auth_service, ops_runtime
        """
    )

    op.execute(
        """
        REVOKE ALL PRIVILEGES
        ON ALL TABLES IN SCHEMA auth
        FROM PUBLIC, app_runtime, auth_service, ops_runtime
        """
    )

    op.execute("GRANT USAGE ON SCHEMA auth TO auth_service")

    op.execute(
        """
        GRANT SELECT, INSERT, UPDATE
        ON TABLE auth.organizations, auth.users, auth.sessions
        TO auth_service
        """
    )


def downgrade() -> None:
    op.execute(
        """
        REVOKE SELECT, INSERT, UPDATE
        ON TABLE auth.organizations, auth.users, auth.sessions
        FROM auth_service
        """
    )

    op.execute("REVOKE USAGE ON SCHEMA auth FROM auth_service")
```

**不要删除文件顶部的迁移版本变量。**

执行：

```powershell
uv run alembic upgrade head
```

然后启动应用，验证原有登录、`/auth/me`、登出和改密流程仍然正常。

### A5.3.3 创建统一的租户事务

新建：

`E:\code\project\harness\backend\app\db\tenant.py`

```python
from collections.abc import Iterator
from contextlib import contextmanager

from sqlalchemy import text
from sqlalchemy.orm import Session, sessionmaker

from backend.app.core.principal import Principal


@contextmanager
def tenant_transaction(
    actor: Principal,
    session_factory: sessionmaker[Session],
) -> Iterator[Session]:
    """每次调用都创建独立 Session 和事务。"""
    with session_factory() as db:
        with db.begin():
            db.execute(
                text(
                    """
                    SELECT
                        set_config('app.current_org_id', :org_id, true),
                        set_config('app.current_user_id', :user_id, true)
                    """
                ),
                {
                    "org_id": str(actor.org_id),
                    "user_id": str(actor.user_id),
                },
            )

            yield db
```

它按顺序完成：

1. 创建 Session。
2. 开启事务。
3. 设置组织和用户。
4. 执行业务代码。
5. 正常结束时提交。
6. 出现异常时回滚。
7. 关闭 Session，归还连接。

`set_config(..., true)` 只对当前事务生效。[PostgreSQL 官方说明](https://www.postgresql.org/docs/17/functions-admin.html)

`with db.begin()` 会管理正常提交和异常回滚。[SQLAlchemy 官方说明](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html)

以后业务代码这样使用：

```python
with tenant_transaction(actor, session_factory) as db:
    ...
```

**事务内部不要再调用 `db.commit()`。**

如果提前提交，租户上下文就结束了。后续查询可能进入一个没有上下文的新事务。

需要提前把对象写入数据库、取得生成值时，使用：

```python
db.flush()
```

`flush()` 不会结束事务。

本迁移的降级会删除项目表，只用于可丢弃环境或经过明确规划的回退。本教程验收用测试库重建，不需要降级开发库。

为什么同时写 `USING` 和 `WITH CHECK`？

| 表达式 | 负责检查 |
|---|---|
| `USING` | 原有行能否被读取、更新、删除 |
| `WITH CHECK` | 新插入或更新后的行能否属于当前上下文 |

因此，甲组织连接不仅看不到乙组织项目，也不能通过修改 `org_id` 把甲组织项目搬到乙组织。

为什么有 `NULLIF(..., '')`？

事务上下文结束后，自定义配置可能表现为空字符串。先把它转成 `NULL`，避免把空字符串强制转换为 UUID。

为什么要 `FORCE`？

普通表所有者默认可以绕过 RLS。`FORCE` 让所有者也受约束，但超级用户和 `BYPASSRLS` 角色仍然可以绕过。[PostgreSQL 官方说明](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)

这里策略只授予 `app_runtime`。因此 `migration_owner` 在强制 RLS 后也不能随意读取这些业务行；它负责结构迁移，不能把表所有权当成在线业务访问方案。

### A5.6.4 Service

`service.py`：

```python
import uuid

from sqlalchemy import func, update
from sqlalchemy.orm import Session, sessionmaker

from backend.app.core.authorization import Permission, authorize
from backend.app.core.errors import ApiError
from backend.app.core.principal import Principal
from backend.app.db.tenant import tenant_transaction
from backend.app.models.projects import Project
from backend.app.modules.projects.repository import find_project
from backend.app.modules.projects.schemas import project_summary


def resource_not_found() -> ApiError:
    return ApiError(
        404,
        "RESOURCE_NOT_FOUND",
        "资源不存在",
    )


def get_project(
    actor: Principal,
    session_factory: sessionmaker[Session],
    *,
    project_id: uuid.UUID,
) -> dict[str, object]:
    with tenant_transaction(actor, session_factory) as db:
        project = find_project(
            db,
            org_id=actor.org_id,
            project_id=project_id,
        )

        if project is None:
            raise resource_not_found()

        authorize(actor, Permission.READ_CONTENT)

        return project_summary(project)


def update_project_description(
    actor: Principal,
    session_factory: sessionmaker[Session],
    *,
    project_id: uuid.UUID,
    expected_lock_version: int,
    description: str,
) -> dict[str, object]:
    with tenant_transaction(actor, session_factory) as db:
        project = find_project(
            db,
            org_id=actor.org_id,
            project_id=project_id,
        )

        if project is None:
            raise resource_not_found()

        authorize(actor, Permission.EDIT_CONTENT)

        if project.status == "archived":
            raise ApiError(
                409,
                "PROJECT_ARCHIVED",
                "归档项目只读",
            )

        updated = db.execute(
            update(Project)
            .where(
                Project.org_id == actor.org_id,
                Project.id == project_id,
                Project.lock_version == expected_lock_version,
                Project.status == "active",
            )
            .values(
                description=description,
                lock_version=Project.lock_version + 1,
                updated_at=func.now(),
            )
            .returning(Project)
            .execution_options(populate_existing=True)
        ).scalar_one_or_none()

        if updated is None:
            raise ApiError(
                409,
                "VERSION_CONFLICT",
                "内容已更新，请刷新后重试",
            )

        return project_summary(updated)
```

这里有几个重要顺序：

```text
先查当前组织可见的资源
        ↓
查不到返回 404
        ↓
资源可见后检查动作权限
        ↓
检查资源状态、版本
        ↓
执行更新
```

因此，不需要先判断：

```text
这个 ID 是否存在于其他组织？
```

只要当前组织看不到，就按不存在处理。

PATCH 的 SQL 同时检查版本：

```python
Project.lock_version == expected_lock_version
```

这是原子条件，避免“先读版本正确，随后被别人修改，自己仍覆盖保存”的问题。

服务在事务内构造返回数据，避免事务结束后再依赖 ORM 延迟加载。

```python
class RollbackForTest(Exception):
    pass


@pytest.mark.parametrize("finish", ["commit", "rollback"])
def test_tenant_context_does_not_leak_through_pool(
    finish: str,
    tenant_data: TenantData,
    runtime_factories: dict[str, sessionmaker[Session]],
) -> None:
    factory = runtime_factories["app"]
    first_pid: int | None = None

    try:
        with tenant_transaction(
            tenant_data.alpha_admin,
            factory,
        ) as db:
            first_pid = db.execute(
                text("SELECT pg_backend_pid()")
            ).scalar_one()

            ids = db.execute(
                text("SELECT id FROM app.projects")
            ).scalars().all()

            assert ids == [tenant_data.alpha_project_id]

            if finish == "rollback":
                raise RollbackForTest()

    except RollbackForTest:
        assert finish == "rollback"

    assert first_pid is not None

    # 上一笔事务结束，连接已归还。
    # 这里重新借出连接，但不设置任何租户上下文。
    with factory() as db:
        with db.begin():
            second_pid = db.execute(
                text("SELECT pg_backend_pid()")
            ).scalar_one()

            assert second_pid == first_pid

            context = db.execute(
                text(
                    """
                    SELECT
                        NULLIF(
                            current_setting('app.current_org_id', true),
                            ''
                        ),
                        NULLIF(
                            current_setting('app.current_user_id', true),
                            ''
                        )
                    """
                )
            ).one()

            assert tuple(context) == (None, None)

            rows = db.execute(
                text("SELECT id FROM app.projects")
            ).all()

            assert rows == []

    # 同一连接随后仍能安全服务乙组织。
    with tenant_transaction(
        tenant_data.beta_admin,
        factory,
    ) as db:
        ids = db.execute(
            text("SELECT id FROM app.projects")
        ).scalars().all()

        assert ids == [tenant_data.beta_project_id]
```

这条测试有三个关键设计：

1. 连接池大小为 `1`，没有额外溢出连接。
2. 比较 `pg_backend_pid()`，确认确实复用了同一条数据库连接。
3. 分别验证提交和回滚两个结束路径。

如果只是“第一次开一个连接，第二次开另一个连接”，证明不了连接池没有残留上下文。

| 验证 | 预期 |
|---|---|
| 甲组织读取自己的项目 | 200 |

| 甲上下文插入乙组织行 | 数据库拒绝 |
| 同一池连接提交后无上下文查询 | 空结果 |
| 同一池连接回滚后无上下文查询 | 空结果 |
| 临时移除 RLS 后重建测试库 | 数据库负面测试失败 |
| 恢复 RLS 后重建测试库 | 测试通过 |

你需要能够解释清楚这句话：

> 应用层组织过滤表达业务边界，集中权限模块判断动作是否允许；数据库 RLS 在程序漏写组织条件时继续限制可访问的行。三者同时存在，才能覆盖不同类型的错误。

这套 RLS 方案的前提是：应用可信地设置事务上下文。它用于防范遗漏过滤条件等编程错误，不能把数据库凭据泄露或任意 SQL 执行当成已经解决的问题。
